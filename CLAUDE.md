BUG TWO: `smart_tailor`'S SELF-CRITIQUE PASS ROUTINELY RETURNED A BROKEN ATS SCORE AND GARBLED "CHANGES" TEXT. Reproduced twice in four live runs: `atsScore: 0` (a value the stated rubric can never legitimately produce for a real resume) and a `changes` array either containing the literal string `"[object Object]"` three times, or coherent-but-wrong meta-commentary about its own review process ("No changes were made to the tailoredText section, as it accurately reflects..."). Root cause: `smart_tailor` always runs two AI passes — draft, then a mandatory self-critique/revise — and the critique pass's prompt showed the model a JSON template with literal example *values* (`"changes":[...]`, `"atsScore":0`) instead of the type placeholders pass 1's own prompt correctly uses, so when the critique found nothing to fix, the model had no good instruction for what to put in those fields and either echoed the literal placeholder or invented commentary about the review itself; `normalizeTailorOut`'s `changes` coercion also blindly ran `.map(String)`, turning any object the model did return into literal `"[object Object]"` text. Fixed at both layers: the critique prompt now uses the same type placeholders as the draft prompt, and — since the prompt fix alone did not fully hold under repeat testing — a code-level fallback keeps pass 1's already-valid `changes`/`atsScore`/`scoreReasoning` whenever pass 2 didn't actually change the resume text, and falls back to them even when it did if pass 2's own values come back empty or zero. `normalizeTailorOut` now also pulls a real string out of `{text/description/summary/change/reason}` shapes before falling back to `String()`, rather than trusting the model always returns plain strings. Verified live: 4 consecutive fresh `smart_tailor` calls after the code-level fix all returned real, non-zero, plausible ATS scores and real, specific `changes` describing actual edits — no repeat of either failure mode, versus roughly half of pre-fix runs failing one way or the other.

Neither bug was reachable from the web lane's `tailor`/`match` actions tested earlier this session — `tailor` builds its skill list through `_shared/tailoring.ts`'s `skillsOf()`, which already defensively handles both shapes, and doesn't run a two-pass critique at all. Both bugs were specific to the extension lane's own, separately-written code paths. `npx tsc --noEmit` clean after each of the three edits. Preceded by v3.100.0, asked directly to fix v3.99.0's flagged Kubernetes gap-detection miss, then to test more before calling it done.

DETERMINISTIC GAP DETECTION WAS DROPPING SHORT, SINGLE-WORD REQUIREMENTS EVERYWHERE, NOT JUST ON DISPLAY. Traced past the first, shallow fix. `_shared/tailoring.ts`'s `terms()` (splits a requirement line into countable words) has always had a hardcoded 3-character floor, meaning "Go", "AI", "C#", "R", "ML" reduce to an empty term list regardless of where they're called from. That floor was hit twice: once in `extractRequirements()` (a bullet like "- Kubernetes" needs 2+ real terms of 3+ chars to survive as a tracked requirement at all — one-word bullets never had a chance), and again, more seriously, inside `computeGap()`'s own matching loop, which re-derives the same term list to score coverage — so even a requirement that did survive extraction with a short/single term could still compute to zero terms and get silently dropped a second time, before it was ever checked against the resume. This second drop is why raising the bar in extraction alone (a first attempt) still missed "Go" in testing: fixing the front door didn't fix the back door reading the same list.

Fixed by parameterizing `terms(s, minLen = 3)` and calling it with `minLen 1` at both real sites: `extractRequirements`'s bullet branch (`- Kubernetes`, `- Go`, `- AWS` all now register as real, trackable requirements) and `computeGap`'s coverage computation (a one-word requirement can now actually be scored, not just recorded). Prose lines keep the stricter 8-char/2-term floor unchanged — a stray short fragment in free-flowing text is still more likely noise than a genuine one-word ask; only a bullet, already a deliberate single item by construction, gets the lower bar.

THAT FIX ALONE OPENED A SECOND, REAL GAP — CAUGHT BY THE "TEST MORE" INSTRUCTION, NOT GUESSED AT. Lowering the bulletish threshold to catch "- Kubernetes" also let generic filler bullets through for the first time: "- 5+ years of experience", "- Bachelor's degree preferred", "- Strong team player" all now had a non-empty, non-stopword term ("of", "player") and survived extraction as tracked "requirements" — meaning the new confirm-first UI from v3.99.0 would have shown the person a button to "add" a skill literally named "Strong team player." Fixed with a second, narrow denylist regex (`GENERIC_QUAL`) checked against the whole bullet text before it's tracked: years-of-experience phrasing, degree/bachelor's/master's language, and the common soft-skill set (communication, team player, problem-solving, self-starter, fast-paced, detail-oriented, work independently, interpersonal, time management, organizational/leadership/analytical/people skills, multi-tasking). None of these are real, addable skills, so none belong in a "missing skill" suggestion regardless of how the bullet is worded.

VERIFIED WITH FOUR LIVE TESTS AGAINST THE ACTUAL DEPLOYED FUNCTION, INCLUDING THE ONE SCENARIO NEVER TESTED BEFORE. Same test account and resume (skills: Python, PostgreSQL, Docker, Git) as v3.99.0. (1) A JD with `- AWS / - Kubernetes / - SQL / - Go / - AI / - C#` as separate bullets: all six now correctly flagged missing, where before only the multi-word ones were caught. (2) A JD with `- 5+ years of experience / - Bachelor's degree preferred / - Excellent communication skills / - Python / - Terraform / - Strong team player / - Ability to multi-task in a fast-paced environment`: missing came back as exactly `["Terraform"]` — the one genuine gap, with every soft-skill/quals bullet correctly excluded. (3) A prose-style JD ("Strong experience with distributed systems and microservices architecture...") under a real "Requirements:" heading: all three genuine multi-word gaps still correctly flagged, confirming the existing prose-matching path has no regression. (4) The scenario v3.99.0 never covered: added "Go" to the test account's own skills via direct SQL, then ran a JD requiring Go — "Go" correctly did NOT appear in `missing` (it matched), while AWS and Kubernetes, still genuinely absent, correctly did. This closes the loop the first fix left open: a short skill can now be recognized as present, not just recognized as absent.

Preceded by v3.42.0, locking the credit functions against a real concurrent-overspend race flagged during the v3.41.0 admin panel walkthrough.

CREDIT FUNCTIONS LOCKED AGAINST CONCURRENT OVERSPEND. `billing_ensure`, `credit_spend` and `credit_grant` each did a plain read-balance-then-write with no row locking, and all three are independently callable (`resume-hub` calls all three directly; `stripe-webhook` calls `credit_grant` directly; `credit_spend` also calls `billing_ensure` internally). Two near-simultaneous calls for the same user — a double click, two tabs, a retry after a slow-but-successful response — could both read the same starting balance before either committed, both pass the sufficiency check, and both write a deduction: a real overspend, not just a cosmetic ledger mismatch. Flagged rather than fixed during the v3.41.0 walkthrough since it needed a locking-strategy decision, not a one-line patch. Fixed with a per-user `pg_advisory_xact_lock(hashtext(user_id::text))` taken as the first statement in all three functions: it serializes concurrent calls for the same user only (different users never block each other), needs no schema change, auto-releases at transaction end even on error, and works for a brand-new user with no `subscriptions` row yet (unlike locking an existing row, which `billing_ensure` is what creates in the first place). Advisory locks are reentrant per transaction, so `credit_spend` taking the lock and then calling `billing_ensure` (which takes the same lock again) is a safe, instant no-op re-acquire, not a deadlock. Verified with two synthetic concurrent `credit_spend` calls sharing one balance: no overspend, final balance matched the ledger sum exactly, and the second call was correctly refused for insufficient funds once the first had already spent it down.

## What AYN is

AYN is a job search product with two sides.

For job seekers: a Chrome extension that reads the job posting off the page, scores it against their resume and profile, and generates a tailored resume and cover letter for that specific role. Plus Resume Hub, a web app holding one resume, one profile, saved jobs, and proposals.

For employers: a chat that turns a described role into a structured spec, searches candidates who opted into discovery, returns the three best fits with the evidence behind each, and lets them send an assessment or a job proposal. Contact details are shared only when the candidate accepts.

Stack: React and Vite frontend, Supabase (Postgres, pgvector, edge functions, auth, storage), Stripe for billing, Chrome MV3 extension.

Matching: a deterministic prefilter on extracted skills, then vector recall, then a grounded rerank. Candidates are never invented and skills are tagged extracted or inferred.

One repo, one Supabase backend (project dfkoxuokfkttjhfjcecx). Solo founder: Ghazi. Site ayn.careers (moved from aynn.io in v3.85.0). Deployed via Lovable (project a2fa8496-aed3-4f21-93fc-bbbabc069583) which pushes to this GitHub repo.

## Global rules (apply everywhere)

1. GENERATED, never hand-edit: public/ayn-extension.zip and public/ayn-extension-version.json. Run node extension/build.mjs.
2. Version bump protocol: manifest.json version + content.js AYN_BUILD fallback, then build.mjs (which rewrites the version file).
3. Never write to the applications or job_applications tables. Both trackers are deprecated and the Tracker UI was deleted in v3.0.1.
4. The extension is read only. Never add code that writes to, clicks, or types into a page.
5. User-facing writing style: no em dashes, no en dashes, ranges use "to". This rule is also baked into the AI system prompts in cc-generate and resume-match.
6. servers: server.js is the express static host for dist/ (SPA fallback, caching for /assets and /frames). backend/server.py is a FastAPI health stub only, not a real backend. The real backend is Supabase edge functions.
7. memory/PRD.md describes an older platform-era snapshot; trust the docs/map files over it.
8. scripts/check-wiring.mjs must pass; it verifies sidepanel messages have handlers, extension actions are registered, and Hub actions are session-reachable.


## The nervous system (how signals actually flow)

```
                    ayn.careers (Resume Hub)
                    │  AYN_PROFILE_UPDATED / AYN_PING / handoff deep link
                    ▼
 job page ───► extension sidepanel + background.js ───► resume-hub edge fn ───► Supabase tables
 (content.js         JD resolver ladder                 (14 ext actions,          (jobs, resumes,
  read only)         score / tailor / cover / ask        2 auth lanes)             ai_result_cache)
                    ▲
                    └── saved jobs, scores and applications ──► Hub tabs read the same tables
```

Four loops carry everything:

1. READ LOOP: content.js extracts the JD from the live page (site selector map, JSON-LD and meta fallback); the background JD resolver ladder (manual paste, current page, opener tab, registry, listing fetch, backend lookup) upgrades it until jdQuality >= 45. Everything downstream is grounded on that text.
2. SYNC LOOP: profile edited in the Hub -> AYN_PROFILE_UPDATED clears the extension's cached identity -> next read refetches. 24h TTL is the fallback for closed browsers.
3. GAP LOOP (v3.1.0): _shared/tailoring.ts computes matched / missing / nice-to-have deterministically from the JD against structured sections, the model only surfaces and phrases, and the same analysis is returned to the sidepanel so the user sees what is genuinely missing from their background.
4. HANDOFF LOOP: Hub tailors a resume for a job -> deep link carries resumeId -> sidepanel preselects that resume_versions row for scoring, tailoring, and cover letters.
5. MATCH LOOP (v2.9.0-B): seeker opts in -> indexCandidate builds anonymized profile_text + 768d embedding + extracted/inferred skills -> employer_intake_chat distills a JobSpec -> employer_match runs extracted-only prefilter (must-haves), pgvector recall (top 12), then a single grounded rerank on opaque refs (inferred capped at 10 pts) -> top 3 anonymous cards. The ref_map that binds refs to real users never leaves the edge function.
6. PROPOSAL LOOP (v3.6.0): employer opens a card in EmployerHub and reads the full anonymous reasoning -> sends a job proposal (title, location, type, salary, link, message ≤1000 chars) through employer_reveal_request, rate limited to one open proposal per org and candidate and blocked for 30 days after a decline -> the row lands in reveal_requests -> the seeker sees it on the Resume Hub Proposals tab, badged in the rail and first in Home next-actions -> reveal_decide records accept or decline -> ONLY on accept does employer_reveal_status return name, email and phone. Everything before that step is anonymous, enforced in the edge function, not in the UI.


## Honest assessment (strengths, weaknesses, what is actually smart)

STRENGTHS AND MOAT
- Everything AYN now promises runs on our own backend: JD extraction, match scoring, tailoring, cover letters, talent pool matching. No hostile territory, no probability disguised as a guarantee.
- JD grounding is the real asset: a six-tier resolver plus a quality score means the AI is never asked to judge a job from a nav bar and a cookie banner.
- Unified identity (_shared/identity.ts) feeds scoring, tailoring, and cover letters from one place, so quality fixes land everywhere at once.
- Device-token auth (scoped, revocable, no passwords).

WEAKNESSES AND RISKS
- supabase/functions/resume-hub/index.ts is still a large monolith with no unit tests (e2e/ covers the legacy platform, not the extension). content.js is down to ~970 lines after v3.0.0.
- Distribution: sideload only. No auto update, no Chrome Web Store trust signal; users silently rot on old builds. Biggest product risk today.
- The legacy platform roughly doubles repo weight, confuses tooling and new contributors, and its e2e suites can mislead CI signals.
- Bus factor of one (solo founder). These map files are the mitigation; keeping them current is not optional.

WHAT IS ACTUALLY SMART HERE (for an AI forming a mental model fast)
The core insight that survived v3.0.0: on modern job pages, the DOM is a liar and the visible text is the truth. That is why the reader (site selectors, JSON-LD fallback, quality scoring, the resolver ladder) is the part worth defending. Writing to those same pages was the part that could never be made reliable, so it is gone. Judge any proposed change against that split: read deeply, never write.
