# v3.82.0 Four real unauthenticated edge-function security bugs, found by a full source read and fixed live

The v3.81.0 request asked for a four-area audit (edge functions, legacy `SECURITY DEFINER` DB functions, `src/components/`, extension source) alongside the World Intelligence deletion. Ran as four parallel investigations. The edge-function pass is what mattered most: the v3.79.0 audit had curl-tested ~30 functions for auth-*boundary behavior* (does a bad/missing token get rejected) but never read their full source — reading the actual logic is what caught these, since all four correctly reject a garbage token, they just never checked for a token at all.

**`send-notifications`** (`supabase/functions/send-notifications/index.ts`, no local source in this repo before this pass, pulled live via `get_edge_function`). `verify_jwt:false`, zero auth check in the body. Anyone with the public anon key could POST `{type, subject, content, recipient_email}` and have it send a real branded "AYN System" email to that address from `aynn.io`, or pass `user_id` instead to resolve an arbitrary account id to its real email via `auth.admin.getUserById` and message that person directly — `content` was interpolated into the outgoing HTML with zero escaping, a phishing/injection primitive riding on AYN's own sending domain. Its one real caller, `cost-monitor`, is itself already dead (references a `track_user_cost` RPC that doesn't exist — the exact broken-RPC finding v3.79.0 already flagged). No legitimate external caller exists at all. Fixed: locked to service-role-only, the identical "is this call internal" pattern `ayn-unified` already used (`token === supabaseServiceKey`), plus `content`/`metadata` now go through the shared `escapeHtml` from `_shared/emailTemplate.ts` regardless. Verified live: `curl` with the anon key now gets a real `401` for the exact request shape that previously sent a real email.

**`send-email`** (same "no local source" gap). Identical missing-auth problem, but this one has a real, live frontend caller: `AuthModal.tsx:393`'s post-signup welcome email. Unauthenticated, anyone could hit it directly and send any of its 9 branded templates — including a fake "✅ Payment Successful" receipt or a fake "🔐 Password Reset Requested" notice — to any address. The catch: this project has email confirmation on, so `supabase.auth.signUp()` returns no session at the exact instant `AuthModal.tsx` fires the welcome email, meaning that one legitimate call is *structurally* unauthenticated today — requiring a full auth check would have broken real signups. Fixed narrower: every template except `welcome` now requires the actual service-role key as bearer; `welcome` (low-sensitivity, generic content) stays reachable without proof of identity. This is a deliberate, documented residual risk (someone could still spam an arbitrary address a generic "Welcome to AYN!" email) rather than a full close — the real fix is moving the welcome trigger server-side into the unspoofable `auth-send-email` Supabase Auth hook, which is architecture work, not a same-pass patch. Verified live: `curl` with the anon key gets `401` for `emailType: payment_receipt`, still gets a real `200` for `emailType: welcome` — the one real caller's exact shape, unchanged.

**`send-admin-email`** (same gap). Checked only that the caller held *any* valid session via `auth.getUser(token)` — never that they were an admin, unlike every sibling admin-email function (`admin-broadcast`, `custom-auth-emails`, `send-reply-email`, `send-ticket-reply`, `verify-admin-pin`, all of which call `has_role(_user_id, 'admin')`). Any freshly signed-up throwaway account could send email "from" `admin@aynn.io` to anyone. Confirmed zero frontend callers anywhere in `src/` — orphaned from the deleted v3.20.0 admin dashboard — but still directly, unauthenticated-account reachable. Fixed with the identical `has_role` RPC call `admin-broadcast` already uses (`supabase/functions/admin-broadcast/index.ts:63`, copied verbatim for consistency). Verified live two ways: `curl` with only the anon key gets `401` (no session at all); a real throwaway account's own real session token got a genuine `200 success` before the fix and a genuine `403 {"success":false,"error":"Admin access required"}` after, replaying the identical request — this is the actual vulnerability shape (a real non-admin user, not just an anonymous one), confirmed closed. Test account erased after via `erase_account_core`.

**`save-generated-image`** (same gap). No auth check, and zero frontend callers (fully dead feature — old DALL-E image caching, not part of the job-search product). Its only gate on what URL it would fetch and re-host was `imageUrl.includes('oaidalleapiprodscus.blob.core.windows.net')` — a substring check, not a hostname check. A URL like `https://attacker.example/x?q=oaidalleapiprodscus.blob.core.windows.net` satisfied it while the actual fetch target was fully attacker-controlled; the function would then fetch that URL and re-upload whatever bytes came back into the public `generated-images` storage bucket, unauthenticated, returning a public URL to the caller. An open, anonymous fetch-and-publicly-host primitive. Fixed: a real `new URL(imageUrl).hostname === 'oaidalleapiprodscus.blob.core.windows.net'` comparison, plus the same service-role-only lock as `send-notifications`. Verified live: the exact bypass URL above now gets `401` before the fetch is ever attempted.

All four functions had no committed source anywhere in this repo before this pass (a gap of the same shape `auth-send-email` was in before v3.43.0) — all four are now under `supabase/functions/<name>/index.ts`, deployed via `deploy_edge_function`, matching this repo's standing rule of tracking every function's real source once it's touched.

WIDGET INTAKE (src/components/employer/IntakeWizard.tsx). The employer does not free type a role. They answer one question at a time by clicking, with a "type it instead" escape on every step. An opening description is optional and, when given, is run through employer_spec_extract so answered questions are skipped. Sequence:
1. Role title. Text with common title suggestions.
2. Seniority. Buttons: intern, entry, mid, senior, staff or principal, manager, director or above.
3. Must have skills. Chips, max 6, autocompleted from employer_skill_catalog, which only returns skills that exist in candidate_skills for opted in candidates, with a live count per skill so over-constraining is visible.
4. Nice to have skills. Same widget, max 6, optional.
5. Location and remote. Buttons on site / hybrid / remote, plus a location field unless fully remote.
6. Employment type. Buttons: full time, contract, part time, internship.
7. Minimum years. Buttons: any, 2 plus, 5 plus, 8 plus, 10 plus.
8. Work eligibility. Country plus must already be authorised / open to sponsoring.
Then an editable JobSpec summary card. Clicking any line reopens that single widget. "Find candidates" calls employer_match.

RESULTS AND EVALUATION (v3.9.0, src/components/employer/CandidateAskCards.tsx, employer_card_answer). There is no free-form chat anywhere in the product any more. The results chat was removed because it described the role wrongly, contradicted itself on years of experience, and leaked internal refs like c1. Under each candidate sits a row of four question cards: Why this score, What is missing, Compare to the others (hidden when only one candidate came back), What to ask in a screen. THE PROPOSAL MESSAGE (v3.9.0). Opening the proposal dialog fires employer_draft_proposal, which returns a written message citing only the matched requirements. The employer edits it. If drafting fails, the box stays empty and sending still works.

OFF TOPIC RULE. Anything that is not defining the role or evaluating the returned candidates gets one short sentence saying AYN only helps find candidates for a role, then the current intake question again. No answer to the off topic question, no lecture.

CAPABILITY DENIALS, stated plainly when asked. AYN cannot search job boards. It cannot find open roles. It cannot contact candidates beyond sending a proposal. It cannot see candidates who have not opted into discovery.

EVIDENCE RULE. No praise without evidence. Every statement about fit points at something in that candidate's returned profile. No "perfect fit", no "huge asset", no "exactly what you are looking for". Voice rules unchanged: no markdown symbols, no asterisks, no bullet characters, short sentences, no em dashes, no en dashes.

### Credit functions locked against concurrent overspend (v3.42.0)
`billing_ensure`, `credit_spend` and `credit_grant` (`supabase/migrations/20260731122450_*.sql`, patched in `20260803180000_lock_credit_functions.sql`) each did a plain read-balance-then-write with no row locking: read `credit_balance` (a live `SUM(delta)` over `credit_ledger`), decide, then insert a ledger row. All three are independently callable — `resume-hub` calls all three directly, `stripe-webhook` calls `credit_grant` directly, `credit_spend` also calls `billing_ensure` internally — so two calls for the same user close enough in time (double click, two tabs, a retry after a slow-but-successful response) could both read the same starting balance before either committed, both pass the sufficiency check, and both deduct: a real overspend, surfaced while investigating an odd `balance_after` in the v3.41.0 admin walkthrough and flagged there rather than fixed on the spot.

Fixed with `PERFORM pg_advisory_xact_lock(hashtext(_user_id::text));` as the first statement in all three functions. Advisory transaction locks need no schema change, serialize only calls for the same user (different users never contend), auto-release at the end of the transaction even on error or exception, and work for a brand-new user with no `subscriptions` row yet — locking an existing row was not an option there, since `billing_ensure` is what creates that row in the first place. The lock is reentrant per transaction, so `credit_spend` taking it and then calling `billing_ensure` (which takes the identical lock key again) is a safe, instant re-acquire, not a deadlock.

Verified with two synthetic `credit_spend(10)` calls against a shared starting balance of 10 for a throwaway, non-auth-backed uuid (`credit_ledger.user_id` has no FK, so no real account was needed): the first call's own `billing_ensure` call correctly auto-granted the plan's one-time `period_grant` (this test id had never been through `billing_ensure` before, matching the same first-spend quirk noted in the v3.41.0 entry), bringing the true balance to 16 before spending 10 down to 6; the second call then correctly read the post-lock balance of 6, saw it was short of the 10 requested, and was refused rather than allowed through. Final ledger sum matched the returned balance exactly in both calls — no lost update, no negative balance. Test rows deleted afterward.

### The 45 second cold load, investigated (v3.35.0)
Could not reproduce 45 seconds. Measured directly against https://aynn.io with the Navigation Timing API on a signed out landing visit: domContentLoaded ~1.14s, load ~1.16s, 29 JS chunks, ~540KB total transfer. Two real but minor things were found and one was fixed: useFeatureFlags' mount effect called get_feature_flags unconditionally, so a page with two components independently calling useFeature() paid for two full round trips instead of one even though the module level cache already had a fresh, loaded answer; it now only fetches when the shared cache has never loaded. src/App.tsx's PreloadRoutes warms WorldIntelligence, Settings and Pricing chunks via requestIdleCallback, which is a deliberate, idle-scheduled prefetch, not obviously wrong, and was left alone.

The structural finding that actually explains a report like this: the project's database is eu-west-2 (confirmed via get_project), but every edge function response carries x-sb-edge-region: us-east-1, checked three separate times against both resume-hub and stripe-billing. Every DB query inside every edge function call pays a transatlantic round trip on top of whatever the query itself costs, and resume-hub's handlers issue many queries per call, several of them sequential rather than batched. A signed in dashboard load fires multiple separate edge function invocations on mount (ext_bootstrap-equivalent calls, billing, proposals, assessments), each paying its own cross region tax plus a possible cold Deno isolate start after a quiet period; that combination, not anything on the public landing page, is the plausible source of a report this severe, and was not reproduced here because reproducing a cold isolate on a project with recent traffic is not something this investigation could force. Whether Supabase's function region can be pinned to eu-west-2 for this project is a platform setting, not a code change, and was not touched.

### Per account limit overrides and erasure (v3.29.0)
Two gaps left by v3.28.0, both per account, neither per plan nor global.

Limit overrides. account_limit_overrides holds proposals_limit, assessments_limit, searches_limit and monthly_credits for one user, each nullable, plus the reason and which admin set it. Null means fall back to the plan, which stays the default for everyone, and no plan value is ever copied into the row. Zero is a real zero and blocks the action. The one place that decision lives is effectiveLimit in resume-hub, which takes the override only when it is neither null nor undefined, so 0 survives; employerBilling loads the override next to the plan, planLimitReached uses the effective number, and the 402 plan_limit_reached message says the limit was set for this account rather than claiming the plan includes it. The credit path reads the same override: the stripe-webhook invoice.paid handler grants monthly_credits from the override when one is recorded and from the plan otherwise. An override is per user, so it survives a plan change and stays until an admin clears it, which is why the account detail view carries a Limit override badge and prints plan, override and what is in force for all four numbers. admin_set_limit_override and admin_clear_limit_override are admin only and both audit.

Erasure, two levels. admin_erase_account(p_user_id, p_reason, p_confirm_email) deletes the person's content across roughly fifty tables (resumes and resume_versions, cover letters, jobs and matches, user_profile_data and user_profile_canonical, candidate_index and candidate_skills, talent_pool_consent, extension tokens and link codes, learned answers and ask messages, chat, support threads, preferences and settings, restrictions and overrides, profiles and roles) plus their objects in the resumes, attachments, avatars and generated-files buckets, nulls the person out of the operational logs, and keeps what we are obliged to keep: credit_ledger and subscriptions for accounting, and the proposals and assessments an employer sent them, with the candidate reduced to an opaque candidate_ref of the form erased-xxxxxxxx and no name, email or phone. The auth user is banned for a hundred years, its email replaced with an erased+...@erased.invalid placeholder, phone and metadata cleared, identities and sessions deleted. admin_purge_account then removes the auth.users row itself, and only on an account that has already been erased. Both refuse unless has_role says admin, refuse to target yourself or another admin, require a reason, and require p_confirm_email to match exactly; the admin UI makes the admin type it with nothing pre filled and confirms twice before an erase. account_erasures records erased_at, purged_at, the reason and the email at the time, and the high severity security_audit_logs entries survive the purge because they hang off the admin, not the person.

Two things had to move for this to work. The dead on_security_event trigger on security_logs, a leftover of the agents deleted in v3.21.0, called a function that read a table that no longer exists, so every trigger driven security log write failed and blocked the profiles delete; it is dropped. And reveal_requests.candidate_user_id used to cascade from auth.users, so a purge silently deleted the employer's own proposal history; the column is nullable now with ON DELETE SET NULL, which leaves the row with only the opaque ref.

Verified live on 1 August 2026 with two throwaway accounts. An override of proposals 0 and searches 500 with the other two left empty read back as effective proposals 0, searches 500, assessments from the plan and monthly credits 6 from the plan, so zero and null are handled apart. A wrong confirmation email raised "The confirmation email does not match this account" on both erase and purge, erasing yourself raised "You cannot erase your own account", and an account temporarily given the admin role could not be erased and kept its resume. After erase: resumes, jobs, user_profile_canonical, candidate_index, talent_pool_consent and profiles were all at zero rows, credit_ledger and subscriptions still held their row, the proposal read candidate_ref erased-11111111, auth.users held the erased placeholder email with banned_until set, and the audit row existed. After purge: no auth.users row, the account_erasures row carried purged_at, the audit entries were still there, and on the second account the employer's proposal survived with candidate_user_id null and the opaque ref intact.

## Security audit (v3.77.0), duty role removed, 25 old accounts erased, a real erasure bug found live

Asked directly for a security pass. Ran Supabase's own advisor plus a manual review of what it doesn't catch (ownership checks inside functions, storage buckets, RLS policy logic). One real, confirmed bug: `credit_balance(_user_id uuid)` is `SECURITY DEFINER`, took an arbitrary target user id with no ownership check inside it, and was granted to `authenticated` — any signed-in user could read any other user's credit balance via a direct `supabase.rpc()` call, bypassing the app entirely. The app itself only ever calls it from `resume-hub`'s service-role client with the caller's own id, so `authenticated`/`anon` access was never needed; revoked (`20260807005622_restrict_credit_balance_to_service_role.sql`). One narrower, unfixed finding, left for a real design decision rather than patched blind: the guest branch of `ticket_belongs_to_caller()` (v3.53.0) lets any anonymous visitor insert a message into *any* guest support ticket, not just their own, since there's no session tying a guest to their specific ticket — low practical risk (ticket ids are unguessable `crypto.randomUUID()`s, and no SELECT policy exposes guest ticket content the same way), but the real fix is a per-ticket access token issued at creation, not something to improvise mid-audit. Everything else the advisor flagged was already reviewed and accepted in the v3.40.0 audit and unchanged since (the three service-role-only "RLS enabled, no policy" tables, `vector` extension in public schema, leaked-password-protection toggle). DUTY ROLE FULLY REMOVED FROM EVERY REAL ACCESS PATH. ## Real, executed security test pass (v3.78.0) — a QA planning matrix, then why that was replaced

Immediately after v3.77.0's audit, a request for "an exhaustive test matrix" was answered with a static 69-case QA document (test IDs, steps, an unfilled "pending" status column). Told directly, correctly, that this wasn't useful — it described tests, it didn't run them, and this session already has live database and browser access. Agreed, deleted the source file, and re-did the same ground as an actually-executed pass instead.

METHOD. Created 4 disposable accounts directly in the database (2 seekers, 2 employers each with their own org) and seeded one real row in every isolation-sensitive table: a resume, a job match, a discovery listing (`talent_pool_consent` + `candidate_index`), a pending proposal (`reveal_requests`), and a real assessment with a real score and rubric (`assessments` + `assessment_rubrics` + `assessment_results`). Then became each identity via `begin; set local role authenticated; set local request.jwt.claims = '{"sub":"<uid>","role":"authenticated"}';` before each query — this is not a simulation of RLS, it is the literal mechanism PostgREST sets before evaluating a real request's policies, so a query run this way sees exactly what that user's own API call would see. Anon-role and unauthenticated boundaries were additionally verified with real `curl` against the live edge functions and PostgREST endpoint, and the final guest-ticket fix was verified a third way, with a genuine `fetch()` from inside the actual browser origin.

RESULTS: 13 for 13 real cross-boundary attempts blocked. Seeker B could not read Seeker A's resume, job match, or discovery listing. Employer A could not read Org B's org row, membership, or company account. Employer A could not directly read the proposal *they themselves sent* or the assessment score/rubric for the candidate *they themselves assessed* (no employer-facing SELECT policy exists on either — the anonymized view an employer gets is built entirely inside the edge function). Seeker A could not read their own assessment score either — nobody outside the service role can, by design (v3.13.0). Seeker B's `UPDATE` attempt to accept Seeker A's proposal matched zero rows. Seeker A's attempt to write `role='admin'` onto their own `user_roles` row matched zero rows. Calling `get_admin_overview()` and `admin_set_admin_role()` as a non-admin raised `Admin access required` both times. Calling `credit_balance()` for another user's id and calling `match_candidates_by_embedding()` directly (bypassing `resume-hub`'s org-approval and billing checks) both raised a hard `permission denied` — the two SECURITY DEFINER functions this session's earlier audit had locked down actually hold under a real attempt, not just a correct-looking grant. Cross-user storage object reads and anonymous storage reads both returned zero rows. `assessment_rubrics`/`assessment_results`/`profiles` turned out to have **zero table-level grant** to `authenticated`/`anon` at all — a harder lock than the RLS-filtering that was assumed from reading the policy definitions in the earlier audit; only found by actually trying the query and getting a grant-level error back instead of an empty result.

TWO BUGS THAT ONLY SURFACED BY RUNNING THE TESTS. One: the `duty`-role-removal migration from earlier the same day (v3.77.0) had rewired 16 policies from `has_duty_access()` to `has_role()` directly, but `has_role()` had no `anon` grant where `has_duty_access()` did. Invisible under normal use because `TicketForm.tsx`'s guest ticket insert already avoids `.select()`/`RETURNING`, specifically because of a past bug of this same shape — but `INSERT ... RETURNING` re-checks the new row against SELECT policies regardless, and a test that used `RETURNING` hit a hard `permission denied for function has_role` instead of a clean row. Fixed by granting `has_role(uuid, app_role)` to `anon` (`20260807021213_grant_has_role_to_anon_for_returning_safety.sql`) — restores exactly the anon-safety `has_duty_access` already had; `has_role` is a pure boolean read with no side effects.

Two: the `ticket_belongs_to_caller()` guest-ticket gap the earlier audit had flagged and left open was reproduced live, for real. Created a guest ticket as one anonymous session; as a second, unrelated anonymous session, successfully inserted a message into the first one's ticket — confirmed with `INSERT ... (no RETURNING)`, matching `TicketForm.tsx`'s exact request shape, then confirmed a second time with a genuine `fetch()` from the real browser origin against the live API (`201 Created` on both the legitimate ticket-plus-first-message insert and a second `201` confirming the fix doesn't break it; `401` with the real RLS-violation body on the impersonation attempt). Fixed with a per-ticket secret: `support_tickets.guest_token` and `ticket_messages.guest_token`, both `uuid`, generated client-side the exact same way `ticket_id` already is (`crypto.randomUUID()`, never read back from the server) and required to match on every guest write against that ticket from here on (`20260807022017_guest_ticket_access_token.sql`). `ticket_belongs_to_caller(uuid)` was dropped outright rather than left as an insecure second overload alongside the new `ticket_belongs_to_caller(uuid, uuid)`. `TicketForm.tsx` now generates `guestToken` alongside `ticketId` and sends it on both inserts. Existing guest tickets were backfilled a token for hygiene; this changes nothing live since there is no guest-reply UI today to have depended on the old (missing) value. TypeScript types were regenerated from the live schema afterward (`src/integrations/supabase/types.ts`) so `guest_token` is a real, typed column rather than passed through untyped.

CLEANUP AND WHAT WASN'T RE-VERIFIED. All 4 test accounts, every seeded row, and all ticket/message test data were deleted afterward via direct SQL, with one exception: a single inert storage-object metadata row (no real file behind it, path scoped to an already-deleted test user id, in the private `resumes` bucket) that Postgres's own `storage.protect_delete()` trigger correctly refused to remove via direct `DELETE` ("Use the Storage API instead") — left in place rather than fought, since it is unreachable by anyone and carries no real content. This pass covered Phase 1 (RLS/storage/edge-function security) exhaustively; it did not re-run the full functional/browser/billing surface from the earlier planning matrix — most of that (resume upload, scoring, tailoring, the full proposal/assessment marketplace loop) was already genuinely executed with real accounts in the v3.72.0-era end-to-end test earlier in this session, and true cross-browser-engine testing or a real Stripe checkout are genuine environment limits, stated rather than faked.

## Backend + frontend solidity/penetration audit (v3.79.0) — the credit-minting bug, and a bug the audit caused by accident

Asked directly whether the backend and frontend are solid, correctly wired, and free of hacker-penetrable gaps. This pass went beyond the v3.78.0 RLS/isolation battery into a systematic sweep of every privileged database function and every previously-untested edge function, plus a real frontend XSS check.

CRITICAL — credit_grant() AND credit_spend() COULD BE CALLED BY ANY SIGNED-IN USER WITH NO OWNERSHIP CHECK. Queried `pg_proc`/`information_schema.routine_privileges` directly for every `SECURITY DEFINER` function taking a `user_id`-shaped argument and granted to `authenticated`/`anon` — a systematic version of the check that found `credit_balance`'s bug in v3.78.0, this time run against the *entire* population of matching functions instead of one at a time. `credit_grant(_user_id, _amount, _reason, _ref)` and `credit_spend(_user_id, _amount, _reason, _ref)` both trust whatever `_user_id` is passed with zero ownership check in the function body, `SECURITY DEFINER`, directly callable by `authenticated`. Reproduced live: a throwaway account called `credit_grant` with its own id and minted **999,999,999 credits for free**, one call, no Stripe, no admin. The mirror risk on `credit_spend` — draining a real victim's balance by calling it with their known user id — was not separately reproduced but follows from the identical missing check. `billing_ensure(_user_id, _audience)`, called internally by both, has the same gap with a smaller blast radius (can force-create a `subscriptions` row for another user, but the row-creation is `IF NOT FOUND`-guarded so it can't be repeated). Checked `credit_ledger` for prior abuse before fixing: clean — only small real usage amounts and this session's own earlier test entries, no sign anyone found this before it was found here. Fixed by revoking `authenticated`/`anon` execute on all three (`20260807123544_restrict_credit_mutation_functions_to_service_role.sql`), confirmed zero client-side callers in `src/` first (both only ever called by `resume-hub`/`stripe-webhook`'s service-role clients). Re-verified live twice: the identical self-mint attempt now gets `permission denied for function credit_grant`, and a direct service-role call immediately after confirms the real billing path is completely unaffected.

Broadened the same query to catch *any* `SECURITY DEFINER` function granted to a public role with no `auth.uid()`/`has_role`/`has_duty_access` reference anywhere in its source (not just ones shaped like a `user_id` parameter) — this is what would have caught `credit_grant`/`credit_spend` even if their argument had been named something less obviously targeted. Came back clean after the fix: only `get_feature_flags()` (intentionally public, zero arguments, nothing sensitive) and `has_role()` itself (a pure boolean check, by design, the same anon-safety already re-confirmed correct in v3.78.0) remain unguarded.

EDGE FUNCTION SWEEP (~30 functions never individually curl-tested before this pass). One real, likely-intentional privacy finding: `check-email-exists` returns `{"exists":true/false}` for any email to anyone holding the anon key, no rate limit observed — genuine account-enumeration on a job-search platform (knowing someone is job-hunting is more sensitive than average), but almost certainly backing a legitimate "an account already exists, sign in instead" signup flow — flagged for a product decision, not patched blind. Two info-disclosure findings from raw error messages leaking to unauthenticated callers: `admin-pin-alert` echoes a real Resend error ("aynn.io domain is not verified"), which is worth the founder's own look since it may mean actual PIN-security alert emails are silently failing to send in production, not just a cosmetic leak; `cost-monitor` references a database function (`track_user_cost`) that does not exist, a real broken-tracking bug behind the info leak. Neither touched from here — one needs a Resend dashboard check, the other needs a decision about whether cost tracking is still wanted.

A REAL PRODUCTION BUG FOUND BY ACCIDENT WHILE VERIFYING AN XSS FIX. `/nda/:token` and `/sign/:token` — the legacy contract/NDA signing pages, still linked from old client emails per the Routes note in CLAUDE.md — were completely broken for every real visitor: the page always showed "This link is invalid or has expired," even for a real, valid token. Root cause: `sign-document`'s CORS `Access-Control-Allow-Headers` never listed `x-application-name`, a header `src/integrations/supabase/client.ts` attaches to every request via `global.headers` — so `supabase.functions.invoke()` (what `NDASign.tsx` actually calls) triggered a preflight the browser silently rejected client-side, before the request ever reached the server, with no error surfaced anywhere except a browser console CORS message. `resume-hub` and `resume-match` had the byte-identical missing header, but were never actually broken in practice — confirmed why, not just assumed: their one real caller, `src/lib/resumeHub.ts`, uses a raw `fetch()` rather than `supabase.functions.invoke()`, so it never picks up the client's global header config in the first place. Verified this distinction directly: manually replaying the exact header set against `resume-hub` reproduces the identical CORS failure, proving the function was equally exposed to the bug, just never actually triggered by its real caller. Fixed all three (added `x-application-name` to each allow-list — purely additive, no security tradeoff) and redeployed via the Supabase CLI (`supabase functions deploy resume-hub` / `resume-match`, since `resume-hub` is a ~249KB file with shared `_shared/*.ts` dependencies well beyond what a single tool call should carry; `sign-document` — small enough — was redeployed via the direct MCP deploy tool). `verify_jwt` was confirmed and preserved as `false` on all three redeploys, matching their existing anon-facing design.

REAL, REPRODUCED STORED-XSS, ALREADY-LOW-RISK BUT FIXED ANYWAY. `NDASign.tsx` rendered five NDA text fields (`nda_purpose`, `confidential_info`, `obligations`, `exclusions`, `additional_clauses`) as raw HTML through a local `nl2br()` helper that only ever did `text.replace(/\n/g, '<br/>')` — no escaping at all. Reproduced end to end: inserted a real `nda_agreements` row with a `<script>` payload directly in `nda_purpose`, loaded the real page (after the CORS fix above, which this reproduction is what surfaced the CORS bug in the first place), and confirmed the payload would have rendered as live markup. Real-world exploitability was already low going in — `NDAManager`, the old admin UI that created these rows, was deleted in v3.20.0, and a repo-wide grep confirms zero remaining write path into these five columns today, so there is currently no live way for an outside attacker to get content into them — but the missing escaping was a genuine landmine, not a false alarm, and the fix is trivial and behavior-neutral for legitimate content. Added a proper `escapeHtml()` step before the newline conversion. Verified three ways: `tsc --noEmit` clean; then live against the real seeded row in a real browser — the literal text `<script>window.__xss_fired = true</script>` renders as visible plain text, `window.__xss_fired` stays `false`, and `document.querySelectorAll('script').length` shows only the app's own legitimate script tags. Test row deleted after.

METHOD NOTE, worth keeping for future audits of this codebase: the technique that found `credit_grant`/`credit_spend` was querying `pg_proc` for the *entire population* of functions matching a risk shape, not re-checking the handful an earlier pass had already looked at. The v3.78.0 audit had checked `credit_balance` directly and concluded it was fixed and isolated; it never asked "what else looks exactly like this." That question, asked systematically rather than function-by-function, is what surfaced the two worse bugs sitting right next to it.
